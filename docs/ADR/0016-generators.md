# ADR-0016: Completion, documentation and schema generators

Status: Accepted (2026-09-26)

## Context

SPEC.md §4.5 asks for static completion scripts plus runtime value
completion, manpage/Markdown/HTML output, and a JSON description of the
parser that reflects what is *accepted* rather than what help shows.

## Decision

### `hasami-complete`

* One static generator per shell (bash, zsh, fish, PowerShell, nushell)
  over a shared, eagerly built `Node` tree (visible subcommands, options,
  positionals, possible values). Lazy subcommands are built for the tree.
  Hidden items are omitted, as in help. `Shell` implements `FromStr` so a
  `completions <SHELL>` subcommand needs no extra code.
* Dynamic completion protocol, one for all shells: the wrapper script
  sets `_HASAMI_COMPLETE=<shell>`, `_HASAMI_COMPLETE_WORDS` (all words
  joined by `U+001F`, binary name first, current word last) and
  `_HASAMI_COMPLETE_INDEX`, then runs the binary. The binary calls
  `dynamic::complete_from_env(&cmd)` before parsing; it prints one
  candidate per line (`value<TAB>help`, or `value:help` for zsh) and
  exits 0. `U+001F` was chosen over NUL because every shell can pass it in
  an environment variable and no argument contains it in practice.
* `dynamic::complete` walks the typed words with the same rules as the
  parser (subcommands, `--`, options that take a value, short clusters)
  and offers, in order: values for a pending option, `--opt=` values,
  option names, subcommand names, positional values. Value candidates
  come from `Arg::complete_with` (new, an `Arc<dyn Fn(&str) -> Vec<String>>`
  stored in the definition) and from `possible`.
* The bash script is syntax-checked in tests when `bash` is available;
  other shells are checked structurally only.

### `hasami-doc`

* `manpage` (roff with `man` macros; `NAME`, `SYNOPSIS`, `DESCRIPTION`,
  `ARGUMENTS`, `OPTIONS`, `SUBCOMMANDS` with one `.SS` per subcommand,
  `NOTES` for `after_help`), `markdown` (one heading level per depth,
  anchors for subcommands), `html` (standalone page with inline CSS).
  Roff escaping covers backslashes, hyphens and leading dots/quotes.
* Annotations (`[default: ..]`, `[possible values: ..]`, `[env: ..]`)
  are rendered exactly as in `--help` so the three views agree.

### `hasami-schema`

* `to_json` / `to_json_pretty` write a document by hand (no serde) with
  `"format": 1` on the root; every argument, group, `requires` pair and
  subcommand is included, hidden or not, and lazy subcommands are built.
* `JSON_SCHEMA` (draft 2020-12) documents the format and is shipped as a
  string constant so tooling can validate output.
* The document says what the parser accepts (`help_flag`, `version_flag`,
  `value_optional`, `dynamic_completion`), not how help is laid out.

## Consequences

* All three crates depend on `hasami` with the `help` feature (for usage
  lines) and use only public getters (ADR-0015).
* Adding a field to `ArgDef` means adding a getter, a schema property, and
  a bump of `FORMAT_VERSION` if consumers must care.
* The dynamic protocol is stable API: scripts generated by one version
  keep working with binaries built by the next.
